# TASK 2: "Claim fees" button on the Base dashboard, signed in the browser wallet (Rabby)

Commit message: `base: claim-fees button signed in the browser wallet (no server signing)`.

## Goal
On each Aerodrome Slipstream position card (both managers) on the Base dashboard, a "Claim fees" button builds `collect({tokenId, recipient: <NFT's on-chain owner>, amount0Max: 2^128-1, amount1Max: 2^128-1})` for the position's verified manager and sends it with the user's injected EIP-1193 wallet. The Base server still never signs, never reads a keystore, and still refuses every server-side transaction route.

## Findings: how wallet.html signs today (reuse the pattern, not the code)
- `wallet.html` loads ethers 6.13.4 from a CDN (`<script src="https://cdnjs.cloudflare.com/ajax/libs/ethers/6.13.4/ethers.umd.min.js">`, line 18) and uses `new ethers.BrowserProvider(window.ethereum)`, `provider.send('eth_requestAccounts', [])`, `provider.getSigner()`, then either `new ethers.Contract(addr, abi, signer).method(...)` (Approvals tab: `approve`, `setApprovalForAll(operator,false)`, lines 1289-1327; Approve tab `setApprovalForAll`, ~1384) or `signer.sendTransaction({to, data, value})` (Sell l.2408, Mint/close l.2660, 2704). Server-built calldata comes from `/api/approval`, `/api/v4-approval`, `/api/sell/quote`, `/api/mint/*`.
- Chain switching: `wallet_switchEthereumChain` with `'0x' + chainId.toString(16)`, in some tabs followed by `wallet_addEthereumChain` (l.1457-1467, 1669-1675); `accountsChanged` -> `location.reload()`. Status text uses `textContent` or `statusHtml` with `escHtml` on each value; tx links `${explorer}/tx/${hash}` after `tx.wait()`.
- The server signs nothing for these tabs; the browser wallet does. BUT on a `noTransactionData` instance (Base, PulseChain) the server answers 403 for the calldata routes and `wallet.html` hides Sell/Mint (`c.noTx`, l.1520-1525). So on Base there is no existing browser-signing flow to reuse; Task 2 adds one, following the same wallet calls (eth_requestAccounts, chain switch, status + explorer link), but WITHOUT the CDN library and WITHOUT server calldata (see decisions below).
- The Base dashboard page (`dashboard.html` -> `/dashboard.js`) does not load ethers or any wallet code today. Slipstream cards render in `dashboard.js` `positionCard` (~l.3347-3431; `platformMetric` l.3456 currently says "read only: not collected, closed or sold here").
- `slipstream.js` `readPosition` already returns `nftId`, `positionManager`, `staked`, `gauge`, `fee0`, `fee1`, `feesUsd`, `protocol` (the settings name, `aerodrome-v1` / `aerodrome-cl2`), and estimates fees with `npm.collect.staticCall({tokenId, recipient: wallet, amount0Max: MAX_UINT128, amount1Max: MAX_UINT128}, {from: wallet})`. The positions reach the page in `external` of `/api/positions` and in `/api/watch` wallets.

## Design decisions (implementer follows; changes need the orchestrator)
D1. Encoding is done in the browser by a tiny dependency-free module (no CDN, no ethers): `claim-fees-core.js`, UMD (works under `require` in tests and as a browser global), exporting `collectCalldata({ tokenId, owner })` = 4-byte selector of `collect((uint256,address,uint128,uint128))` + 4 static words (tokenId, owner, 2^128-1, 2^128-1). The recipient parameter IS the owner argument; the function has no recipient/amount inputs. `balance`/`ownerOf` reads for verification use the wallet's own `eth_call`.
D2. Server adds ONE read-only route `GET /api/claim-fees/target?protocol=<name>&id=<digits>` (not a transaction route, no calldata, no `to`/`data` fields, answered under `LP_READONLY=1` and `noTransactionData`). It resolves `protocol` against `cfg.contracts.slipstream[].name`, takes the manager address ONLY from that settings entry (the allowlist is exactly those entries, i.e. the two Slipstream managers on Base), requires the id to be a position in the server's current payload (main or watched wallet, `external`), reads `ownerOf(id)` fresh over the server RPC, re-estimates fees with the `collect` staticCall from the owner, and returns `{ ok, chainId, chainName, explorer, manager, tokenId, owner, staked, fee0, fee1, symbol0, symbol1, decimals0, decimals1, feesUsd, feesOk }`. Query parameters named `manager`, `to`, `recipient`, `owner` are ignored. Staked (owner is a gauge / `p.staked`) returns `staked: true`.
D3. New browser module `claim-fees.js` (served by a new static route like `/qr.js`, loaded from `dashboard.html`), the ONLY place containing `eth_sendTransaction`. Flow on click: fetch target -> if `staked` stop -> show a confirmation panel (pair, tokenId, manager short + full in title, owner, estimated fee0/fee1 and USD with "estimate, at current prices") -> `eth_requestAccounts` -> `eth_chainId` must be `0x2105` (8453): if not, `wallet_switchEthereumChain {chainId:'0x2105'}`; on rejection or failure, stop with a message (no `wallet_addEthereumChain`, see M3) -> connected account must equal `target.owner` (case-insensitive, checksummed compare) AND the wallet's own `eth_call ownerOf(tokenId)` at `target.manager` must equal both -> `eth_sendTransaction { from: account, to: target.manager, data: collectCalldata({tokenId, owner: target.owner}), value: '0x0' }` (no gas/fee fields; the wallet estimates) -> show hash (must match `/^0x[0-9a-fA-F]{64}$/`) and link `${target.explorer}/tx/${hash}` (`target.explorer` from the server, https only) with `rel="noopener"`. Wallet error 4001 -> "Rejected in the wallet. Nothing changed." `accountsChanged`/`chainChanged` during a pending panel closes it.
D4. Button markup carries only `data-protocol` and `data-id` (never an address). No text input anywhere: recipient and manager are not user-editable.
D5. Staked (gauge) cards: the button renders `disabled` with visible text and `title`: "Staked in the gauge: trading fees go to the gauge's voters. Rewards are claimed through the gauge, not here." Position with `feesOk === false` or both fees 0: disabled ("nothing to collect" / "fee read unavailable"). Non-Slipstream cards (Uniswap v3/v4, v2 LP) get no button.
D6. `platformMetric` copy changes from "read only: not collected, closed or sold here" to a truthful line for unstaked Slipstream cards on a chain with the feature; the title text on the `tier` pill (l.3354) likewise.
D7. The server code paths (`server.js`, `slipstream.js`, `watch.js`, the new target module) contain no signing: the existing static test in `test/base-instance.test.js` (regex for `sendTransaction|signTransaction|signMessage|new ethers.Wallet|sendRawTransaction|.approve(|setApprovalForAll|.deposit(|.withdraw(|getReward(`) stays and is extended to the new server-side module.

## Design
- New `collector-base.js` (CLI: `node collector-base.js --mode=simulate|collect [--data-dir=DIR]`; `full` from the shell wrapper maps to `collect`). New pure `collector-base-logic.js` (threshold, gas-cap, skip decisions; unit-testable). Only the ABI fragments `ownerOf`, `isApprovedForAll`, `collect` exist in the file. It refuses to run unless `cfg.chainId === 8453` and the RPC reports 8453, and only acts on managers listed in `cfg.contracts.slipstream` (the two Aerodrome managers on the example).
- Hook: `run-collector.sh` calls the Base pass after the existing Robinhood `node collector.js` call, in the same unlocked process context (same env), only when `${LP_BASE_DATA_DIR:-$HOME/base-data}/settings.json` exists. The Robinhood invocation line and everything before it stay byte-identical; Base pass failure never changes the script's exit status or Robinhood's output (`|| echo "...base pass failed" >> base log`). `simulate` mode runs the Base pass as `--mode=simulate` (no keystore decrypt, reads only, the operator address is taken from the keystore's public `address` field exactly as `server.js` l.154-160 does for Robinhood, or skipped with a log line if no keystore). Base log and state go to the Base data dir (`collector.log`, `state.json` inside `$LP_BASE_DATA_DIR`), never to Robinhood's `collector.log` / `state.json`.
- Opt-in flags: `wallets.watched[].collect` (existing field) and a new `wallets.main.collect` (default false; Trading IS `wallets.main` on Base, not a watched wallet, so without this the main wallet could never be enabled). `settings.js` must carry `main.collect` into the flat cfg and through `toLegacy`/`fromLegacy`/`save` without disturbing existing round-trip tests. `settings.base.example.json` gains explicit `"collect": false` on `main`, `Wallet 11`, `Wallet 12`, and a top-level block (not `collector`, which an existing test forbids in the Base example) `"baseCollect": { "minFeesUsd": 2, "minFeesToGasRatio": 5, "maxGasPerRunEth": 0.0003, "maxGasPriceGwei": 1, "maxCollectsPerRun": 6 }` with `_comment`. Defaults apply when keys are absent.
- Per owner with `collect:true`, per configured manager: (1) FIRST `isApprovedForAll(owner, operator)` on THAT manager; false -> log exactly `SKIP <manager name> <owner label> <owner>: operator <operatorAddr> is not approved for all on <managerAddr> (isApprovedForAll=false); no transaction sent, no approval requested` and do nothing else for that pair. Per-token `getApproved` is deliberately not accepted. Nothing in the code calls `setApprovalForAll`/`approve`. (2) `positionsOf(owner)`; skip `staked` (NFT sits in a gauge, operator cannot collect), `feesOk === false`, `feesUsd == null` (unpriced: fail closed), tokens whose owner at send time (`ownerOf`) is not the configured owner. (3) Simulate `collect({tokenId, recipient: owner, amount0Max: MAX128, amount1Max: MAX128})` with `staticCall` from the operator; estimate gas; `gasCostUsd = gas * min(maxFeePerGas, gasPrice) * ethUsd` (ETH/USD from the Base pricing path; if unavailable skip all with a log line). Collect only if `feesUsd >= minFeesUsd` AND `feesUsd >= minFeesToGasRatio * gasCostUsd`. (4) Per-run gas cap: stop sending once estimated + already spent gas exceeds `maxGasPerRunEth`, or the count reaches `maxCollectsPerRun`, or network gas price > `maxGasPriceGwei` (log reason). Also honour a rolling 24 h cap by reusing `collector-logic.js` helpers with the Base `state.json`. (5) Send with `recipient = owner` (the on-chain owner, re-read just before send); wait for the receipt; log tx hash, amounts, gas used; record spend. A failed send is logged and the pass continues to the next position within caps.
- Output format (log lines): one `=== base collect mode=<m> chainId=8453 ===` header, one `--- <label> (<addr>) ---` per owner, one `#<id> <pair> fees $x gas $y -> collect|skip: <reason>` per position, a final `=== base done: n collected, m skipped, gas <eth> ETH ===`.
- LP_READONLY interaction: `LP_READONLY=1` is a property of the Base SERVER process (`server.js` l.76, it refuses to start without it when `noTransactionData` is on) and stays exactly as is: the Base server never signs, never reads the keystore, `OPERATOR` stays null. `collector-base.js` is a separate short-lived process started only by `run-collector.sh`; it does not import `server.js`, does not read or require `LP_READONLY`, and ignores it. Consequence for the written invariants: README (l.~603-652), `settings.base.example.json` comments and the earlier hard constraint H3 ("no signing on new chains") must be reworded to "the Base SERVER is read-only; signing exists only in `collector-base.js`, run by `run-collector.sh`, and only for wallets with `collect:true` whose owner approved the operator". `test/base-instance.test.js` static scan (slipstream/endpoint/verify-onchain have no signing) stays; add a second static scan: `collector-base.js` contains no `swap|exactInput|approve(|setApprovalForAll|transfer|safeTransfer|decreaseLiquidity|burn|withdraw|deposit|exactOutput|Router|Quoter` and its ABI list has exactly 3 functions. This is flagged design-changing in OPEN QUESTIONS (Q1).
- README: new "Auto-collect on Base" section: what it does and does not, config keys, and exact Rabby steps per manager and wallet (owner wallet = the NFT owner, e.g. Trading): 1) open Rabby, select the owner wallet, switch network to Base; 2) open basescan `https://basescan.org/address/<manager>#writeContract` (or `#writeProxyContract` if shown) for each of `0x827922686190790b37229fd06084350E74485b72` and `0xe1f8cd9AC4e4A65F54f38a5CdAfCA44f6dD68b53` (check the address character-by-character; the two are the managers of `aerodrome-v1` and `aerodrome-cl2`); 3) "Connect to Web3" -> Rabby; 4) find `setApprovalForAll(operator address, bool approved)`, `operator` = the collector's operator address (shown by `./run-collector.sh simulate`, line `Operator: 0x...`, never type it from memory), `approved` = `true`; 5) "Write", review the Rabby prompt: it must say Base, the manager as the contract, "Approve all NFTs" style warning for the operator address; confirm; repeat for the second manager; 6) verify with the Read tab `isApprovedForAll(owner, operator)` = true; 7) then set `collect: true` in `$HOME/base-data/settings.json` and run `./run-collector.sh simulate`. To revoke: same call with `approved=false`. RISK paragraph: `setApprovalForAll` lets the operator key transfer, burn-via-decrease, or sell EVERY Aerodrome position NFT of that wallet on that manager on Base, not only collect fees; the operator key is cached in `/dev/shm` while armed (see unlock window), and any process of the same user can read it; the code only calls `collect`, but an attacker with the key is not bound by the code; mitigations: keep the unlock window short, revoke when not needed, keep only the positions you accept this for in that wallet. Also state the Windows task: `windows-task.ps1 -At 8am` (the script defaults to 9am) and that nothing changes in how the task is registered.
